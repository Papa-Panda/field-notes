## 一句话总结

Late Chunking 把 RAG 入库流程从「先切块、再逐块编码」改为「先整篇编码、再按块边界池化 token 向量」，让每个块的向量天然带上全文上下文，几乎零成本地提升检索质量。

## 核心

1. **问题/背景**：普通 RAG 先把长文档切成小块再逐块编码，每个块编码时只看得见自己——跨块的指代信息被一刀切断。例如后一块只剩「它是古代的军事防线」，其中「它」指谁，该块的向量里完全没有，搜「长城」自然召回不到。
2. **机制/方法**：反过来走。先把整篇文档一次性送进长上下文编码器，注意力让每个 token 都看过全文，得到一排「已吸收上下文」的 token 向量；然后才在向量层面划定块边界，把每个块覆盖的 token 向量取平均（池化）得到块向量。文字不重编，只是把算好的向量按块汇总。用的是同一个编码器、同一批文字，唯一差别是切与编的先后顺序。
3. **关键证据或数字**：改动只多一步平均池化，几乎不增加计算成本，也不需要重新训练模型，任何长上下文编码器都能直接套用；收益是每个块向量都带上了全文语境，指代类信息不再丢失（视频未给具体检索指标数值）。
4. **结论/判断**：很多 RAG 召回问题不在模型而在入库流程；当文档长、跨块指代多时，先修切块/编码顺序比换更大的 embedding 模型更优先。

## 可迁移

- 排查 RAG 效果差时加一项检查：抽查召回失败的块，看其向量是否缺失前文指代信息——若是，先切后编就是根因，换 Late Chunking 即可。
- 适用边界要清楚：该方法依赖长上下文编码器能一次吃下整篇文档，超长文档仍需先分段；它解决的是块内缺上下文，不替代重排（rerank）等召回后处理。

## 疑问 / 下一步

- 块边界若切在语义中间，池化后的向量会不会被两段语义稀释，与重叠切块（overlap）如何配合，值得结合 Jina 的评测数据看。
