2一句话总结

7B
FP16

Decode 是 memory-bound：单用户理论 TPS 完全由 HBM 带宽除以模型权重大小决定，7B FP16 在 H100 上限约 240，实测打三到五折属正常。

3核心

  1. 问题/背景：面试常问 7B 模型在 H100 上的理论极限 TPS，多数人第一反应查算力——错了，decode 阶段的真正瓶颈是显存带宽。先要分清两种口径：单用户 TPS 等于 ITL 的倒数（流畅度），系统总 TPS 等于 batch 大小除以 ITL（吞吐），同一 ITL 两种 TPS 完全不同，这是第一坑。
  2. 机制/方法：decode 每生成一个 token 必须把全部权重从 HBM 读一遍。7B 模型 FP16 权重量约 14 GB，H100 的 HBM 带宽是 3.35 TB/s，相除得到理论最小 ITL 约 4.2 ms，倒数即单用户理论 TPS 约 240。这个数与算力无关，是带宽刻出来的上限。
  3. 关键证据或数字：实测通常只有约 100，折扣来自三处：KV cache 也要从 HBM 读，上下文越长等效带宽被稀释越多；每次 forward 发射几十上百个 kernel，启动与调度开销在小 batch 时占比不小；HBM 实际有效带宽只有标称的约 70%–80%。合起来业内经验是理论值的约 30%–50%。
  4. 结论/判断：调大 batch 能让系统 TPS 近乎线性上涨（权重读取被多个请求摊薄），但 KV 总量与排队会把 ITL 从约 50 ms 推高到 80–100 ms；最佳 batch 在算力刚吃满、显存未爆、P99 延迟达标的拐点。于是单用户体验与系统吞吐本质是一对矛盾：小 batch 适合在线聊天、代码补全等实时交互，大 batch 适合离线批处理、评测与训练数据生成。推理框架的核心工作就是在 ITL 不爆的前提下把 batch 拉到最大；面试答权衡时落点是看 SLO 的 P99 反推 batch 上限。

5可迁移

  • 估任何模型的 decode 上限都用同一公式：权重字节数 ÷ 带宽，先算上限再谈优化，避免拿算力（FLOPS）错估吞吐。
  • 给推理服务定容量时把 KV cache 的带宽占用单列：长上下文场景下它才是 ITL 恶化的主因，而不是权重。
