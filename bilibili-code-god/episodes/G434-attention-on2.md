## 一句话总结

自注意力要求每个 token 与全部 token 两两算相关度分数，配对数天然是 $n^2$ ，计算与显存同为平方级，这正是早期模型上下文被卡在 2K–4K 的根源。

## 核心

### 1. 问题 / 背景

早期大模型一次能读入的长度常卡在 2000–4000 token，再长就又慢又贵。瓶颈不在模型「不够聪明」，而在它的核心机制自注意力本身的成本结构。

### 2. 机制 / 方法

自注意力的语义是：每个 token 为了确定自己的含义（比如某个代词指代谁），都要回头与序列中所有 token 逐一比对，算一个相关度分数。设序列长为 $n$ ，则第一个 token 要算 $n$ 次、第二个也要算 $n$ 次，合计 $n \times n = n^2$ 次配对。这些分数排成的表恰好是一张 $n \times n$ 的方阵，即注意力矩阵，格子数就是 $n^2$ 。

关键在平方的放大效应：长度翻一倍，矩阵不是变大一倍，而是变大四倍。视频里的小例子是 4 个 token 对应 16 个格子、8 个对应 64 个、16 个对应 256 个——边长每涨一点，面积按平方膨胀，成本曲线是一条越翘越陡的抛物线。

而且这张矩阵不只是算得慢，它还要实实在在地驻留在显存里，显存占用同为 $n^2$ 量级。算力和显存两头夹击，长文本直接跑不动——这是早期上下文长度被摁在 2K–4K 的直接原因。

### 3. 关键证据或数字

见下方关键数字表：核心就是「长度 ×2 → 计算与显存 ×4；长度 ×4 → ×16」。

### 4. 结论 / 判断

破局思路都是围绕打掉这个 $n^2$ ：一是稀疏注意力，只让每个 token 看邻近或少数重点 token，配对数直接降下来；二是线性注意力，用数学近似把复杂度压回接近线性；三是 FlashAttention，它不改复杂度量级，但换算法大幅省下显存占用。靠这些，今天的模型才能一次读进几十万字。

## 关键数字

| 量 | 基线 → 变化 |
|---|---|
| token 数 4 → 8 → 16 | 注意力矩阵格子 16 → 64 → 256 |
| 序列长度翻倍（×2） | 计算量与显存 ×4 |
| 序列长度 ×4 | 计算量与显存 ×16 |
| 早期模型上下文上限 | 约 2000–4000 token |

## 可迁移

- 面试答这题的逻辑链可以直接套用：两两配对 → $n \times n$ 矩阵 → 长度翻倍成本翻四倍 → 算力与显存双爆 → 早期上下文被卡 2K–4K → 稀疏 / 线性 / FlashAttention 三路破局。
- 做 RL rollout 与长上下文推理的成本估算时，要把 prefill 阶段的注意力计算按序列长度平方计价：prompt 变长一倍，注意力部分成本是四倍，这直接影响 batch 与并发的取舍。
