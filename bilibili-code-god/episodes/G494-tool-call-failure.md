## 一句话总结

Agent 循环天生没有停止键，工具失败又是常态，所以必须给循环装两类护栏：防死循环的刹车（步数/时间上限、循环检测、熔断器）和防乱回答的诚实机制（结构化错误喂回上下文、明确终止态、兜底降级）。

## 核心

1. **问题/背景**：Agent 的工作方式是一个「思考 → 调用工具 → 看观察结果 → 再思考」的循环，循环本身不会自己停。工具随时会失败（超时、参数错误、服务器崩溃、限流、返回空），没有护栏时只有两种失控方式：一是反复重试同一个失败调用烧光 token，二是工具明明失败却编一个自信的假答案。
2. **机制/方法**：先修错误上报方式——在 MCP 里失败不应抛异常（协议级错误模型读不懂），而应返回正常结果并把 `is_error` 设为 true、带结构化错误码和一句人话说明，让模型能「看见」错误并推理。再装刹车：步数上限（逻辑闸）+ 执行时间上限（钱包闸）；把「工具名+参数」做哈希，同一调用出现三次即判定卡死并中断；重试要带退避且次数克制。再加熔断器：连续失败超阈值就从 closed 跳到 open 直接快速失败，冷却后 half-open 放一个试探调用，成功回 closed、失败回 open。最后装诚实护栏：把结构化错误喂回上下文、给模型明确的终止态（如 SUCCESS / FAILED），加 grounding 指令「没拿到就说没拿到」，并预备兜底（默认值/缓存、反问用户、升级给人）。
3. **关键证据或数字**：LangChain 默认步数上限是 15；死循环现场里同一个失败调用被重试到第 47 次，token 账单从三千烧到五十万全是无效消耗。
4. **结论/判断**：让 Agent 强大的是循环，让 Agent 靠谱的是循环上的护栏；快速失败永远好过慢慢死，好 Agent 要敢说「我不知道」并给出下一步选项。

## 关键数字

| 项 | 数值 |
|---|---|
| LangChain 默认步数上限 | 15 |
| 同一调用重复出现判定卡死 | 3 次 |
| 重试次数建议上限 | 3–5 次（带退避） |
| 无护栏死循环的 token 浪费 | 三千 → 五十万量级 |

## 可迁移

- 做 Agentic RL / Agent 框架时，把步数上限、超时、循环检测、熔断做成 harness 层的默认配置，而不是指望模型自觉停下——这也是 rollout 成本控制的第一道闸。
- 面试答 Agent 工程题可套用「刹车 + 诚实」框架：先讲错误结构化（is_error + 错误码），再讲四道护栏，最后落到兜底降级与转人工。

## 疑问 / 下一步

熔断器的失败阈值和冷却时间怎么按工具类型调参，视频没展开；实际系统里可能还要结合工具的历史成功率做动态阈值。
