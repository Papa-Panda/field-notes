2一句话总结

温度为 0 时同一 prompt 两次结果不同，真凶不是浮点并发随机，而是内核缺乏 batch 不变性——规约顺序随并发 batch 大小而变；换上 batch 不变内核后，RL 采样器与训练器逐位一致，训推 KL 恒为零。

3核心

  1. 问题/背景：浮点加法不满足结合律，规约顺序一变结果就变。流行解释是 GPU 上万线程并发规约、先后随机；博客指出这是错的：单个内核逐次运行的规约顺序是固定的、结果完全可复现。真正的问题是 batch 不变性缺失：一个内核的输出不应依赖这次一起算了多少条序列，但现实中 RMSNorm、矩阵乘、注意力都会按 batch 大小选并行策略（小 batch 把一行拆给多个核做 split 规约，大 batch 一行一核），策略一变规约顺序就变；而推理服务的 batch 由同时到达的请求数决定，于是同一输入的结果取决于同一时刻别人在发什么请求。
  2. 机制/方法：三个算子各一招。RMSNorm 用数据并行规约，一个核负责一个 batch 元素，无论 batch 多大都不拆行；矩阵乘固定 tensor core 指令与分块，小 batch 用 padding 补齐而不是换策略；注意力最难，KV cache 分块时用固定的 split 大小而不是固定的 split 数量，这样序列长度变化时规约顺序也不变。
  3. 关键证据或数字：代价是未优化的确定性 vLLM 慢 2.1 倍，改进注意力内核后慢 1.6 倍，矩阵乘比 cuBLAS 慢约 20%，且作者称优化投入还很少。对 RL 的实验更关键：无确定性、无 off-policy 修正时，采样器与训练器算出的概率不一致，KL 约 0.001 且带尖峰，reward 最终崩掉；用确定性内核后两边逐位一致、KL 恒为零，RL 第一次真正 on-policy，不需要任何重要性修正。
  4. 结论/判断：先确认根因——单请求重复跑一致、并发下不一致，就是 batch 不变性问题而非随机种子。要不要上确定性看场景：评测可复现、RL 训推一致值得慢 1.6 倍，线上高吞吐服务未必。与 TIS/MIS 这类修正对比：它们治标，确定性内核治本。

4关键数字

项 数值
确定性 vLLM 速度代价 2.1 倍 → 优化后 1.6 倍
矩阵乘 vs cuBLAS 慢约 20%
非确定性下训推 KL 约 0.001 带尖峰 → 确定性后恒 0

5可迁移

  • RL infra 的 on-policy 纯度：训推 KL 不归零时先排查内核 batch 不变性（尤其注意力的 split 策略），而不是先加重要性采样补丁。
  • 面试可讲：浮点不结合律 + 动态 batching 如何让「确定性解码」在服务负载下失效，以及固定规约顺序的三种实现手法。
