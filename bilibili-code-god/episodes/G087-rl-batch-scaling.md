## 一句话总结

大 batch 的 rollout 吞吐更高，但要同时算两笔账：算法上学习率须按 $\sqrt{B}$ 缩放才保住每样本学习量，系统上只有吞吐增益大于样本惩罚时加大 batch 才真的省时间。

## 核心

1. 问题/背景：RL 一步分 rollout 采样与参数更新两段。自回归生成在低并发时是显存带宽受限——每生成一个 token 都要把整套权重搬一遍、算得少搬得多；并发加大后一次搬运服务更多序列，吞吐上升（PPO 中 batch 256→1024 响应收集吞吐 2.29 倍，GRPO 中 prompt batch 512 比 128 快 1.36 倍）。但吞吐不等于学得快。
2. 机制/方法：第一笔账是算法层：batch 变大则每步梯度更准但步数更少，学习率需按 Adam 下的根号缩放，新学习率等于原学习率乘以 $\sqrt{B/B_0}$ ；这样调后学习曲线在一段范围内近似 batch 不变（GRPO prompt batch 64–1024、PPO 256–2048 都对得上），超出范围梯度范数不再按 $1/\sqrt{B}$ 下降、规则失效——这是初始化规则不是保证。第二笔账是样本惩罚 $R_N$ ：达到目标分数所需的总样本数，大 batch 比小 batch 多出多少倍；不变区间内 $R_N$ 约为 1，prompt batch 到 2048 与 4096 时升到 1.6，即多烧 60% 样本。决策不等式：新配置时间更短当且仅当吞吐比大于 $R_N$ ；吞吐涨 1.36 倍而样本惩罚 1.6 倍，就是花钱买慢。
3. 关键证据或数字：GRPO 在 Qwen3-30B-A3B 上 prompt batch 1024 配根号缩放学习率，归一化时间到目标为 0.71（省 29%），1024 以上反而更慢；不调学习率直接加 batch，吞吐更高却更慢。PPO 在 3B 激活的混元 MoE 上结论一致。
4. 结论/判断：加 batch 的正确顺序是两步：先调训练侧——batch 变了学习率按 $\sqrt{B}$ 缩放，看学习曲线是否与小 batch 重合、确认在不变区间内；再测系统侧——端到端吞吐增益是否大于样本惩罚。两条都过才加；且不变区间有上限（GRPO 约到 prompt batch 1024），再往上先测 $R_N$ 。

## 关键数字

| 指标 | 数值 |
|---|---|
| PPO rollout 吞吐（batch 256→1024） | 2.29 倍 |
| GRPO 样本惩罚 $R_N$（prompt batch 2048/4096） | 升至 1.6 倍 |
| GRPO prompt batch 1024 + $\sqrt{B}$ 缩放 | 时间到目标省 29% |

## 可迁移

- RL 训练调参纪律：batch 与学习率联动是硬规则，任何只报吞吐不报样本效率的扩 batch 方案都不可信；把「时间到目标分数」而非 tokens/s 作为扩容决策指标。
- 面试答「RL batch 怎么定」：带宽受限解释吞吐、根号缩放保学习量、决策不等式收尾，三段式完整。
