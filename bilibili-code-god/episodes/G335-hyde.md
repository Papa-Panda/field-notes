## 一句话总结
先让 LLM 给短 query 生成一段「假想答案」，再用这段长文本去检索——检索发生在答案与文档之间，语义粒度对齐后零样本检索质量提升约 10%–20%。

## 核心
1. **问题/背景**：用户 query 又短又模糊（如「怎么治失眠」），文档却是长段详细说明；短句与长文在 embedding 空间里天然距离远，这是 RAG 检索答非所问的根本瓶颈——query 与文档的语义粒度不匹配。
2. **机制/方法**：三步——LLM 根据 query 生成一段假想答案（可以是错的，但要写得像模像样）；把假想答案编码成向量去检索真实文档；用检索到的文档回答原始 query。核心洞察是：一段详细回答与另一段讲同一件事的详细回答向量距离很近，因为句式、用词、信息密度都相似；HyDE 本质是把 query 从「问题空间」转换到「答案空间」再检索。
3. **关键证据或数字**：原论文在 TREC DL19/DL20、BEIR 等零样本 benchmark 上，nDCG 相对直接用 query 检索平均提升 10%–20%，且无需任何训练、纯靠 prompt。代价是每次检索多一次 LLM 调用，成本与延迟翻倍；对查事实、找数字这类答案本身很短的任务帮助不大。
4. **结论/判断**：假想答案不需要正确，只需要「看起来像答案」——错的答案照样能搜出对的文档；它最适合开放域问答、需要详细解释的场景。

## 关键数字
| 项 | 基线→结果 |
|---|---|
| 零样本检索 nDCG | 直接 query 检索 → 提升约 10%–20% |
| 额外成本 | 每次检索 +1 次 LLM 调用 |

## 可迁移
- RAG 排障第一性原理：先看 query 与文档的粒度/分布是否对齐，再谈换 embedding 模型；query 改写、HyDE、多查询扩展都是同一类「分布对齐」手段。
- 面试答法：HyDE 的关键句是「检索的钥匙不必是对的，但必须是像的」——用生成文本的 embedding 做语义桥，而不是事实来源。

## 疑问 / 下一步
