## 一句话总结
训练显存的大头不是权重而是梯度和优化器状态：权重、梯度、Adam 两份动量合计至少是推理的 4 倍，RLHF 还要再养多个模型。

## 核心
1. 问题/背景：同一模型推理跑得好好的，一训练就爆显存。根源在反向传播：训练除了存权重，还要存梯度、存优化器更新所需的状态，账要逐项算。
2. 机制/方法：三大件按权重份数计——权重 1 份；梯度与参数一一对应，1 份；Adam 要同时维护一阶、二阶动量，2 份。三大件合计 4 份。再加激活值（随层数、batch size、序列长度涨）、框架计算图与缓存等开销，所以按参数量只能估数量级，实际占用通常更高。
3. 关键证据或数字：换 SGD（只存一份状态）则是 3 倍。RLHF 更夸张：PPO 同时加载 actor、reference、reward、critic 四个模型，其中 reference 与 reward 只存权重不更新，actor 与 critic 还要各自背梯度和优化器状态，总量是推理的数倍；DPO 合并了奖励与 RL 两步、只更新 actor，约为推理的 5 倍以上——这也是能砍掉 critic 的方法吃香的原因。
4. 结论/判断：答这道题先给「权重 1 + 梯度 1 + Adam 2 ≥ 4 倍」的骨架，再补激活与框架开销，最后按 PPO/DPO 的模型个数往上加。

## 关键数字
| 场景 | 显存（以推理权重为 1 份） |
|---|---|
| 推理 | 1 份 |
| 训练 + SGD | 约 3 份 |
| 训练 + Adam | 至少 4 份（另加激活等） |
| DPO | 5 倍以上 |
| PPO（四模型） | 推理的数倍 |

## 可迁移
- 做 RL 训练显存预算时，先按「几个模型在训、几个只推理」列清单再逐项乘份数，比直接套 4 倍更不容易爆。
- 这也解释了 GRPO/DPO 类去 critic 方法在 RL infra 里的显存红利：少养一个带优化器状态的模型。

## 疑问 / 下一步
- 混合精度下权重/梯度/动量的 dtype 组合（如 fp32 主权重 + bf16 计算）会把份数账改成字节账，实际估算时应按字节重算一遍。
