2一句话总结

MCP 与 Skills 不是二选一：MCP 是连接协议、解决「连得上」，Skills 是行为规范、解决「做得对」；真实工作流是 Skill 当总指挥、需要动手时经 MCP 调工具。

3核心

  1. 问题/背景：给 Agent 加能力时常纠结该用 MCP 还是 Skills，但两者根本不在同一层：一个向外打通工具，一个向内规范流程。
  2. 机制/方法：MCP 是标准化连接协议，把模型与数据库、API、文件、第三方服务统一接通，只管提供标准化的调用方式、权限与格式，不关心业务逻辑（像墙上的标准插座）。Skills 把一套标准作业流程固化成可复用技能包，定义任务目标、执行步骤、判断条件与输出格式（像操作说明书）。
  3. 关键证据或数字：省 token 是 Skills 的突出优势，靠渐进式披露 + 内容外部化：启动时只加载每个 Skill 的名字与一句话描述（仅几十到上百 token），请求命中后才读详细流程，参考文档、模板、schema 都留在外部按需读取；对比之下 MCP 的工具定义常驻上下文，挂五六个服务、还没开口就吃掉数万 token。
  4. 结论/判断：分工口诀——连接靠 MCP、方法靠 Skills，缺一不可；例如用 MCP 接上 GitHub，再用一个 Skill 教 Agent 按团队规范审查 PR。

4关键数字

项 量级
每个 Skill 启动加载成本 几十至上百 token（仅名称 + 描述）
挂 5–6 个 MCP 服务的常驻成本 数万 token（工具定义全量驻留）

5可迁移

  • 搭 Agent 时的选型顺序：先盘点需要连哪些外部系统（MCP 层），再沉淀高频任务的 SOP（Skills 层），不要把流程逻辑硬塞进工具描述里。
  • 上下文预算视角：工具定义常驻成本随接入服务数线性膨胀，Skills 的按需加载是控制长上下文开销的直接手段。
