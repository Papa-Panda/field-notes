## 一句话总结

教科书说梯度累积等价于大 batch，前提是每个小 batch 的 loss 归一化方式一致；变长 SFT 里若每个小 batch 各自除以自己的有效 token 数再平均，短序列 token 的权重会被放大一个数量级，loss 系统性偏高、累积步数越大偏得越多——修法是交叉熵先求和、最后除以整个累积窗口的总有效 token 数。

## 核心

1. **问题/背景**：显存装不下大 batch 时拆成几个小 batch、梯度攒够再更新，线性叠加看似严格等价。但大模型 loss 是按 token 算的：一个 batch 内所有有效 token 的交叉熵求和除以有效 token 数（padding 标 -100 不参与）。文本变长时，各小 batch 的有效 token 数差很多（例子里 100 vs 1000），各自归一再平均，分母就乱了。
2. **机制/方法**：数字代入最直观：短序列 100 个 token、平均每 token loss 3.0（总和 300），长序列 1000 个 token、平均 2.0（总和 2000）。正确的大 batch loss 是 2300/1100 ≈ 2.09；朴素累积先各自平均再平均得 2.5，系统性偏高。本质是权重错位：短序列每个 token 的权重被放大约 10 倍，而短序列缺上下文、loss 天然更高，于是整体 loss 被进一步抬升；Unsloth 的对比图里累积步数 1/2/4/8 的 loss 曲线依次抬高，本该完全重合。多卡 DDP 同病：每卡各自按本地 token 数平均、再跨卡平均，犯的是同一个错。
3. **关键证据或数字**：该 bug 在 HF Trainer 里存在约两年，几乎所有用它训过变长 SFT 的人都受影响；等长序列（如定长 4096 packing 的预训练）分母恒定，不受影响。
4. **结论/判断**：修法一句话——分母用整个累积窗口的总有效 token 数：交叉熵用 sum 而非 mean，累积开始前先数好窗口内总有效 token 数、最后除一次。HF 在 Trainer 里加了 `num_items_in_batch` 参数传给模型的 loss 函数，多卡时先把各卡 token 数 all-reduce 求和；2024 年 10 月之后的 transformers 版本默认已修，但自定义 loss、自写训练循环、老版本都必须自己接这个参数，否则 bug 复现。

## 关键数字

| 量 | 正确（按总 token 归一） | 朴素累积（各自平均再平均） |
|---|---|---|
| 示例 loss | 2300/1100 ≈ 2.09 | (3.0 + 2.0)/2 = 2.5 |
| 短序列 token 权重 | 与长序列一致 | 放大约 10 倍 |

## 可迁移

- 自查方法极便宜：同一批数据把累积步数设为 1 和 4 各跑几步，loss 应几乎重合，不重合就是分母错了——这条可进任何自写训练循环的冒烟测试。
- 面试被问「梯度累积等不等价于大 batch」：答定长等价、变长必须按 token 归一，并能说出 HF 的 `num_items_in_batch` 修法与 DDP 下先 all-reduce token 数的细节，是很硬的工程加分项。

## 疑问 / 下一步

- 同类「各自归一再平均」的坑在多任务/多数据源混训的 loss 加权里也会出现（每个数据源内部平均再按权重混合），值得顺手排查自己的框架是否按全局 token 数归一。
