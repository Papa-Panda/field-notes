## 一句话总结

指令遵循的约束一半能用代码精确查、一半只能靠模型判：VerIF 把硬约束交给 Python 脚本二值校验、软约束交给推理模型逐条判断，两路分数取平均当 RL 奖励，在只用英文单轮数据训练的情况下泛化到多语言、多轮和未见过的约束类型。

## 核心

1. 问题/背景：指令遵循的回答要同时满足若干约束。硬约束（长度、关键词、格式、标签）可以写代码精确检查；软约束（内容相关、风格、语气）没法写规则，只能让模型判。旧做法两头不讨好：只用硬约束，模型学会钻空子（字数够了、内容空洞）；全交给 LLM 裁判，慢、贵、还不稳——尤其是形式类约束裁判反而判不准。
2. 机制/方法：VerIF 做成验证工程三步：先造数据——VerInstruct 约 2.2 万条指令、平均每条 6.2 个约束、每个约束都带验证信号，其中 22.3% 是硬约束、77.7% 是软约束；再两路验证——硬约束用 Python 脚本二值校验，软约束用推理模型 QwQ-32B 逐条判断；最后合成奖励——两路分数取平均（不是乘积），单个硬约束不满足不会一票否决。
3. 关键证据或数字：在 Tulu 3 SFT 8B 上做 RL，IFEval prompt 级严格分从 68.4 涨到 84.5（+16.1），超过 Tulu 3 正式版的 79.7 且用的额外数据少得多；Multi-IF +15.8、FollowBench +9。训练只用英文单轮，多语言、多轮、未见约束类型都涨；GSM8K、MMLU-Pro、BBH 等通用能力持平或略升。泛化好的原因是奖励教的是"读清要求、逐条对照"的行为，而不是某条具体约束。
4. 结论/判断：实操四条：先把约束拆成硬/软两类，能写代码的绝不交给裁判；软约束裁判要用推理模型，换裁判要重新验证；奖励取平均，别让单个约束一票否决；训练时监控通用基准，指令遵循 RL 不应以通用能力为代价。

## 可迁移

- 这是 verifier 设计的通用范式：可验证的交给代码（精确、便宜、防钻空子），不可验证的交给裁判（补内容与风格），两路互补而不是二选一；和 RLVR 里"先 fuzz 判卷器"是同一套验证工程思路。
- 面试讲指令遵循 RL 时，给出约束拆分比例（约两成硬、八成软）和"平均而非乘积"的奖励合成细节，比只说"用 LLM 当裁判"具体得多。

## 疑问 / 下一步

- 软约束裁判本身也有偏差与可利用空间，VerIF 用的是固定裁判；裁判与策略同训或裁判被策略反向利用时，奖励质量如何监控，值得继续看。
