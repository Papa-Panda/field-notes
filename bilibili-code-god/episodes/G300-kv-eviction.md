## 一句话总结

注意力高度稀疏——超过 95% 的 KV 几乎无人关注，因此在固定 KV 预算下只需保留「重击者」token 与最近 token，H2O 在生成中按累积注意力分数贪心驱逐，SnapKV 用提示词末尾的观察窗口投票、一次性压缩长提示词。

## 核心

1. **问题/背景**：KV 缓存随序列长度线性膨胀，长上下文下动辄吃掉数 GB 显存，还没开始回答显存先爆。但把注意力矩阵摊开看，它稀疏得惊人：超过 95% 的格子接近零，真正被反复关注的永远是少数 token（重击者，heavy hitters），输出主要由他们主导。
2. **机制/方法**：固定预算（如只留 1000 份 KV）下，保留两类：被反复关注的重击者、以及紧邻当前位置的最近 token（下一个词最依赖眼前上下文）；其余低注意力又不靠窗的路人 token 是驱逐对象。H2O 给每个 token 记累积注意力分数，生成中边写边清，缓存超预算就踢掉「分数最低且不在最近窗口」的那个，贪心地永远只留高分者加最近一小段。SnapKV 面向超长提示词：它发现哪些 token 重要，用提示词结尾一小段就能看出来——划出观察窗口，让窗口内 token 对前面全部内容投票，票高者入选并带上相邻 token 防信息切碎，在读完提示词后一次性压缩，而非逐步清理。
3. **关键证据或数字**：两者内核一致——注意力是稀疏的，与其把显存平摊给每个 token，不如把预算全压在关键少数上；效果是 KV 显存能砍到只剩零头、长文本推理明显更快，而答案质量几乎不掉。
4. **结论/判断**：两者分工不同：H2O 盯生成过程（边生成边淘汰，靠累积分数），SnapKV 盯长输入（读完一次性压缩，靠窗口投票）；选型按瓶颈在 prefill 还是 decode、提示词长还是生成长来定。

## 关键数字

| 量 | 数值 |
|---|---|
| 注意力矩阵中接近零的比例 | 超过 95% |
| 保留对象 | 重击者 token + 最近窗口 token |

## 可迁移

- 面试答 KV 优化谱系：压缩（量化）、共享（MQA/GQA/MLA）之外还有驱逐这条线；驱逐的合理性论证就一句话——注意力稀疏、重击者主导输出。
- 做长上下文推理服务时，KV 预算应显式设为可调参数，并区分 prefill 压缩（SnapKV 式）与 decode 期驱逐（H2O 式）两个阶段分别治理。

## 疑问 / 下一步

- 累积注意力分数偏向早期 token 时，中段关键信息被误逐的风险有多大，H2O/SnapKV 在 needle-in-a-haystack 类评测上的召回损失值得核对。
