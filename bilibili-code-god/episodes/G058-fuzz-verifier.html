2一句话总结

可验证奖励不是数学定义而是一条软件流水线，判卷器的 bug 会被 RL 当成可利用的漏洞学进模型——训练前要用 fuzzing 加变形测试像测软件一样测 verifier，先把假阳/假阴率量出来。

3核心

  1. 问题/背景：RLVR 的奖励来自代码：解析输出、抽取答案、校验格式、与标准答案比较、给分。这条流水线每一层都可能出错，而且 RL 不会报错——优化压力会把假阳性（错答被判对）放大成模型可利用的漏洞，把假阴性（对答被判错）变成白白丢掉的训练信号。
  2. 机制/方法：把软件测试搬过来：一是用 fuzzing 自动生成大量对抗性补全，喂给数学判卷器、JSON 校验器、代码测试框架，同时用一个更严格的参考实现做成对判决，对不上的地方就是 bug，输出假阳率、假阴率、分歧率、可利用点数量、不确定度五个指标；二是用变形测试抓假阴——对已知正确答案做证明等价的变换（加空格、换分数写法、改单位、加尾句号），正确性不变则判决必须不变，变了就是 bug；反过来对错误答案做变换，若被判对就是假阳。
  3. 关键证据或数字：2026 年 9 月的品类审计显示，默认 LaTeX 配置下 93% 的判卷失败来自空格和标点（尾随句号、换行），而非 LaTeX 解析本身；自验证准确率随配置从 53.8% 到 95.2%，差 41.3 个点；同一个判卷库的两个版本在 49.9% 的测试对上判法不一致；数值比较用相对容差导致台阶函数：1 万以下差 1 的答案全拒、1 万以上差 1 的全收。
  4. 结论/判断：落地五条：训练前跑一遍 fuzz 与变形测试量出假阳/假阴率；锁定 verifier 版本，升级必须重新体检；数值比较用绝对加相对容差，不要只用相对；先做格式归一化（去尾句号、去空白、统一分数与小数）；每次判决记进日志，reward 异常时能回溯是不是判卷器在给假分。

5可迁移

  • 做 RLVR / agentic RL 环境时，verifier 应按软件工程标准管理：版本锁定、回归测试、判决日志；reward 曲线异常先怀疑判卷器，再怀疑模型。
  • 面试聊 reward hacking 时可以落到这一层：很多"模型作弊"其实是判卷器先有洞，fuzz + 变形测试是训练前成本最低的一道防线。

6疑问 / 下一步

  • 变形测试依赖"等价变换"的构造，目前主要覆盖数学答案格式；开放域任务（如代码生成、Agent 轨迹）的等价变换与参考实现怎么造，仍是难点。
