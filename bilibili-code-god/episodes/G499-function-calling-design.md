## 一句话总结

Function Calling 会在参数格式、工具选择、多步链路三处崩；对应解法是约束解码锁格式、工具检索收窄候选、校验重试闭环兜底，三层缺一不可。

## 核心

1. **问题/背景**：模型本身不执行代码，只是依据放进请求里的工具 JSON Schema 生成一段结构化 JSON，程序解析后真正执行、把结果塞回对话再循环。单独看机制简单，实跑却有三处崩点：参数瞎编与格式违规（结构复杂的真实场景下合规率能跌到一成出头；面对没训练过的 API 库，大量调用是凭空编出来的）；工具一多选择就崩（说明书从几千 token 涨到十几万 token，选择准确率最多能掉 70–80 个百分点）；多步调用中途断链（最强的模型完整走对全流程的概率也只有约 28%）。
2. **机制/方法**：三层防护一一对应。约束解码：把 Schema 编译成语法规则，生成时实时把不合法字符的概率清零，格式合规率可顶到 100%——但它只保证「长得对」，治不了选错工具、编造不存在取值这类语义幻觉。工具检索：像搜索引擎一样先检索出与本次提问最相关的少数工具，再让模型在小候选池里选；OpenAI 建议一次给模型的工具不超过 20 个，Anthropic 更建议把功能相近的工具合并成更少更强的工具。校验重试：执行前先用程序校验参数与类型，不通过就把具体报错原样喂回模型重新生成——关键是给外部真实报错信号，而不是让模型自己空反思。
3. **关键证据或数字**：工具全量硬塞时选择准确率仅 13.62% ，先检索再选跳到 43.13%（三倍多），且请求 token 省一半以上；加上校验重试闭环，工具调用的修复成功率从 6.8% 提到 26.4% ；复杂 Schema 下用约束解码的模型合规可达 100% ，不用则老模型不到 40% 。
4. **结论/判断**：约束解码保证的是看起来对，检索与校验兜的才是真的对；设计 Agent 工具层时三层要叠加落地，而不是指望模型自觉。

## 关键数字

| 指标 | 无防护 | 加防护 |
| --- | --- | --- |
| 工具选择准确率（全塞 vs 先检索） | 13.62% | 43.13% |
| 调用修复成功率（校验重试闭环） | 6.8% | 26.4% |
| 复杂 Schema 格式合规（约束解码） | < 40% | 100% |

## 可迁移

- Agentic RL / Agent 工程：轨迹质量的一大噪声源就是工具调用失败，三层防护（约束解码、工具检索、校验重试）应作为环境侧的标配，而不是让策略模型在脏反馈里学。
- 面试答 Function Calling 稳定性时按「三崩点 → 三解法 → 各自数字」组织，并点明约束解码治标（格式）不治本（语义），是加分细节。
